## Branches and Pull Requests

Every change should be made in its own branch, created from `main`. Please don't commit directly into the `main` branch.

1. Name your branch as `type/short-description`, using the same types as [Conventional Commits](https://www.conventionalcommits.org/):
   - `feat/` for new features or commands
   - `fix/` for bug fixes
   - `docs/` for documentation changes
   - `refactor/` for code changes that don't alter behavior
   - `test/` for adding or adjusting tests
   - `chore/` for maintenance tasks

   Use lowercase and hyphens in the description, e.g. `fix/streak-reset-bug` or `feat/export-command`.

2. Commit your changes, preferably following the Conventional Commits style as well.
3. Open a Pull Request against `main` and reference the related issue in the description.
4. I'll review it and may ask for adjustments before merging. 

## Project layout

```
main.go                  wires the database and the TaskManager into cobra
internal/db/queries/     SQL for sqlc (todos.sql, todos_history.sql, dump.sql)
internal/db/schema/      goose migrations, embedded in the binary
internal/db/out/         code generated by sqlc (do not edit by hand)
internal/tasks/          the service: business rules, returns data, never prints
internal/commands/       cobra commands; render.go prints the CLI output
internal/tui/            the Bubble Tea interface; uses the same tasks service
pkg/color/               themes and Lip Gloss styles
pkg/i18n/locales/        en.json and pt.json
```

The CLI and the TUI both call `internal/tasks`, so a feature usually means:
one service method, then a command that prints its result and/or a TUI
action that draws it.

## Adding a command

1. **Query.** If no existing query covers it, add one to the matching file in
   `internal/db/queries/` and regenerate the code:

```sql
-- name: DeleteTodoByName :exec
DELETE FROM todos
WHERE name = ?;
```

```bash
sqlc generate
```

   A schema change needs a new migration in `internal/db/schema/`
   (`00N_description.sql`, with `-- +goose Up` / `-- +goose Down`).

2. **Service method** in `internal/tasks`. It takes `ctx` first, **returns
   data** (usually `TodoView`), and never prints. Wrap errors with `%w`, and
   return the sentinels from `errors.go` (`ErrTodoNotFound`, `ErrNotDaily`)
   when a caller may want to react with `errors.Is`:

```go
// DeleteByName removes the task that best matches name and returns it, so
// callers can show which task the fuzzy search actually picked.
func (tkm *TaskManager) DeleteByName(ctx context.Context, name string) (TodoView, error) {
	row, err := findTodoByName(ctx, tkm, name)
	if err != nil {
		return TodoView{}, err
	}

	if err := tkm.Queries.DeleteTodoByName(ctx, row.Name); err != nil {
		return TodoView{}, fmt.Errorf(i18n.T("tasks.error.deleteTaskByName"), err)
	}

	return viewFromNameRow(row)
}
```

3. **Command** in `internal/commands/commands.go`. Validate the input, call the
   service with `cmd.Context()`, then print. Larger outputs get a `print…`
   function in `render.go`. `printQuote()` shows a random quote:

```go
var delByName = &cobra.Command{
	Use:     i18n.T("commands.commands.delByNameUse"),
	Short:   i18n.T("commands.commands.delByNameShort"),
	Aliases: []string{"deln", "dn"},
	Args:    cobra.MaximumNArgs(1),
	RunE: func(cmd *cobra.Command, args []string) error {
		if !deleteYes {
			return errors.New(i18n.T("commands.error.destructiveAction"))
		}

		tkm, err := taskManagerFromContext(cmd.Context())
		if err != nil {
			return err
		}

		taskName := name
		if len(args) > 0 {
			taskName = args[0]
		}

		todo, err := tkm.DeleteByName(cmd.Context(), taskName)
		if err != nil {
			return err
		}

		color.MsgSuccess(fmt.Sprintf(i18n.T("tasks.info.taskDeletedSuccessfully"), todo.Name))
		return nil
	},
}
```

4. Register the command in the `commands` map inside `init()`, and add its
   flags there too ([cobra flags guide](https://cobra.dev/docs/how-to-guides/working-with-flags/)):

```go
delByName.Flags().StringVar(&name, "name", "", i18n.T("commands.flags.delByNameName"))
delByName.Flags().BoolVar(&deleteYes, "yes", false, i18n.T("commands.flags.delByNameDeleteYes"))
```

5. **Texts.** Every message goes through `i18n.T("section.group.key")`. Add the
   key to **both** `en.json` and `pt.json`. Don't name a key `id`,
   `description`, `hash`, `leftDelim`, `rightDelim`, `zero`, `one`, `two`,
   `few`, `many` or `other`: go-i18n reserves them in nested messages, and the
   whole file then fails to load.

6. **TUI (optional).** If the TUI should use it too, add the method to the
   `Service` interface in `internal/tui/model.go` and to `fakeService` in
   `model_test.go`. Run the call as a `tea.Cmd` that returns a message (see
   `deleteCmd` in `actions.go`).

## Tests

```bash
gofmt -l .          # must print nothing
go mod tidy -diff   # must print nothing
go vet ./...
go test -race ./...
```

The same checks run in GitHub Actions (`.github/workflows/ci.yml`) on every
pull request and on pushes to `main` and `dev`: on Linux with the race
detector, and on Windows (build and tests). A pull request should only be
merged with both jobs green. Tests of Unix-only features (systemd install,
the `serve` lock, file permissions) skip themselves on Windows.

- Service tests use `newTestTaskManager(t)`, which creates a temporary
  database with every migration, so they never touch your real data.
- TUI tests drive the model with key messages and a `fakeService`, without a
  terminal.
- To try the binary without touching your data, point it at a temporary
  database and config:

```bash
DB_PATH=/tmp/akrasia-test.db XDG_CONFIG_HOME=/tmp/akrasia-config go run . init
DB_PATH=/tmp/akrasia-test.db XDG_CONFIG_HOME=/tmp/akrasia-config go run .
```

### Releasing

Releases are automatic: pushing a version tag runs
`.github/workflows/release.yml`, which builds the Linux, Windows and macOS
binaries and publishes the GitHub release with that version's changelog
section as its notes. The tag is not tied to the PR or branch name; it is a
pointer to a commit that you create yourself after the merge.

1. On `dev`, rename `[Unreleased]` in `CHANGELOG.md` to `## [2.6.0] - date`
   (and leave a fresh empty `[Unreleased]` above it).
2. Open the PR `dev` → `main`, wait for CI to be green and merge it. The PR
   title is free; the workflow does not read it.
3. Tag the merge commit on `main`:

```bash
git checkout main && git pull
git tag v2.6.0
git push origin v2.6.0
```

4. Follow the run in the Actions tab. When it finishes, the release is under
   Releases with the binaries, `checksums.txt` and the changelog notes.

Things to remember:

- A plain `git push` does not send tags; push the tag by name (or use
  `git push --tags`).
- Tag `main` after the merge. Tagging `dev` before it releases the code of
  `dev`.
- The tag must match a changelog section: `v2.6.0` looks for `## [2.6.0]`.
  If it is missing the workflow fails and publishes nothing.
- Do not also create the release by hand on GitHub; the workflow already
  does. To redo a failed release, delete the tag and the release, fix the
  problem and tag again:

```bash
git tag -d v2.6.0 && git push origin :refs/tags/v2.6.0
```
